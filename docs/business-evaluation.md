# 业务工具配对评测（M2）

Evo 的新实验把“两个版本是否加载了不同内容”扩展成“在相同业务场景上分别完成了什么”。候选仍由人工创建；自动诊断、候选生成和推荐版本准入属于 M3。

## 如何使用

1. 在 `/settings` 配置模型，在 `/evo` 创建基线和有实际内容变化的候选。Pi 支持策略与原生 Skill，DSH 当前支持任务指令前缀。
2. 选择评测范围，检查文件 diff 和总预算，再点击“验证两个版本”。
3. 查看双版本通过数、有效覆盖、逐题结果、总预算和执行证据。执行异常不计为答题失败，未知用量不计为零。

| 范围 | 计划 | 用途 |
| --- | --- | --- |
| 开发冒烟 | 每类第一道开发题，共 3 题 × 双版本，默认 1 次 | 检查工具、运行器、加载和验收链路；不支持晋升结论 |
| 验证对比 | 6 道验证题 × 双版本 × 2 次 | 预声明质量门槛的父子对比 |
| 封存报告 | 6 道封存题 × 双版本 × 2 次 | 最终报告，结果不用于候选生成或选择 |
| 旧任务加载检查 | 修正帮助语义的订单回执题 × 双版本 | 兼容 M1；旧实验保留原始任务指纹 |

API：`POST /api/evo/experiments`，请求头 `X-EvoArena-Request: 1` 和 `Idempotency-Key`。例如：

```json
{
  "baseline": "已保存的父版本 ID",
  "candidate": "对应子版本 ID",
  "mode": "smoke",
  "limits": {"calls": 72, "tokens": 600000, "seconds": 2400}
}
```

`validation` / `report` 默认重复 2 次，API 可设 `repeats: 3`；不得降到 1 次。重复请求使用原键返回原实验，更改版本、范围或预算必须使用新键。`GET /api/evo/taskpacks` 返回任务分组和指纹，不包含故障答案。

## 任务包的 18 种机制

任务是隔离的模拟业务服务，Agent 真正通过终端工具调用服务；没有真实客户或支付。`inspect` 提供当前可用动作和公开契约，`help` 完全本地且无副作用。时序由动作驱动，避免宿主机负载改变故障时机。每个 Trial 都重建状态。

| 问题族 | 开发（2） | 验证（2） | 封存（2） |
| --- | --- | --- | --- |
| 下单结果核对 | 已落库但回执超时；受理后异步完成 | 请求在落库前失败；状态读暂不一致 | 订单已存在；异步受理最终拒绝后可重试 |
| 完整订单对账 | 多页结果；索引未完整需刷新 | 不透明游标；分页重叠需去重 | 快照变化需重启扫描；后页包含更高版本取消记录 |
| 订单履约与补偿 | 已有库存占用；确认步骤暂时失败 | 库存占用成功但回执丢失；确认永久拒绝需补偿 | 取消成功但回执丢失；库存冲突须取消 |

不同分组有不同故障机制。对账数据还使用不同订单 ID 和金额，减少记忆开发题答案的收益。三组各含 6 个实例，仍是小规模机制评测，不是行业通用能力基准。

## 可信执行与判定

- TaskPack 以任务、分组、提示、业务服务、CLI、中继、验证器、适配器与执行代码的内容哈希寻址；数据库禁止覆盖。源码变化时生成新包，已有包执行前检测漂移。
- 计划在派发前固定任务、角色、版本、重复编号和预算；相邻重复交替先执行基线/候选。镜像解析为本地内容 ID 后使用专属快照标签，两版同题的 Harbor 任务 checksum 必须一致。
- 当前供应商未声明可固定 seed，计划显式记录 `seed_support=provider_not_declared`。重复执行不保证逐 token 重现。
- Agent 容器离线，只挂载模型/工具中继与只读版本；业务真值、验收脚本及验证密钥不进入 Agent。宿主机维护签名业务账本，独立验证容器只读挂载。
- 运行器结束（包括可处理的超时）后，宿主机标记关闭业务入口，后续中继请求被拒绝。验证结果再签名，宿主机核对结果签名、冻结标记、Harbor reward 和加载证据。Agent 可写的日志不是验收信任根。
- 判定先核对完整有效覆盖，再检查各题重复后的成功数没有下降、总成功数严格增加、关键约束零违反。结果分为 `improved`、`unchanged`、`regression`、`insufficient_evidence`。只有完整验证集的 `improved` 才有 `gate_eligible=true`，M2 不更新任何推荐版本。

## 预算与中断

每个 Trial 仍限制为 240 秒、12 次模型请求和 180,000 个报告 Token；实验另有总请求、总 Token、总时限。界面可在启动前调整总预算，验证/封存默认 288 次请求、240 万 Token、9,600 秒。未配置价格时不估算金额。

每次模型派发前，SQLite 同一事务写入调用意图并占用总请求；收到响应后幂等结算实际用量。调用记录只存请求哈希，不存凭据。供应商失败、未报告用量、进程中断留下的待结算调用会阻止后续派发；最后一个响应可能跨过 Token 阈值。总时限包含环境准备，收尾清理可能继续数秒。

M2 支持持久计划和总账，尚不支持从中断位置自动续跑。重启将活动实验标为 interrupted，不重放业务副作用；取消、资源对账、Trial 边界恢复和 epoch fencing 属于 M4。不要据此把当前版本当作无人值守生产调度器。

## 校准与实际证据

运行 `python -m unittest discover -s tests -p test_business.py -v`。校准策略仅使用公开工具响应，覆盖全部 18 题：正确解通过，空操作和典型错误解拒绝。独立 Node 验证器还检查签名被改动、跨 Trial 密钥、错误任务的账本均被拒绝。测试同时覆盖预算重开、重复结算、用量未知、冻结后的副作用拒绝、任务指纹错配、缺失结果与逐题退化。

真实运行记录、版本、总账及 Trial 工件保存在本机 `.evoarena/`。M2 的脱敏验证摘要见 `m2-verification.json`；它记录开发冒烟的范围，不替代完整验证和封存报告。初次集成运行与最终任务包运行分开记录，未把原型证据改写为新协议证据。
