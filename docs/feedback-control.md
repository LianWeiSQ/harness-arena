# 开发反馈与无反馈对照

对照回答一个具体问题：在相同模型、初始资产、搜索次数和评测预算下，读取开发执行反馈是否比只读取任务目标更有效。它不比较不同模型，也不预设进化一定成功。

`POST /api/evo/experiments` 的自动改进请求可指定 `feedback_mode`：

- `development`（默认）：诊断和生成读取开发集执行证据。
- `none`：仍执行同样的 6 次开发基线，但这些结果、轨迹、耗时和用量不传给生成器。输入只有初始资产和三类公开任务目标；观察引用 `P0001` 等公开契约，不能声称已经观察到运行失败。

两种方式最多各生成一个候选，最多两次诊断/假设调用（含一次结构修正）、一次文件生成，以及 24 次验证（6 题 × 2 重复 × 双版本）。执行模型、目标文件、逐题预算、实验上限和准入规则固定。匹配的是搜索机会与预算上限，实际 Token 可能不同，必须分别报告，不能用空调用补齐支出。

对照使用独立项目保存推荐，不能覆盖反馈实验的推荐。反馈方式进入不可变实验意图；检查点恢复不能切换组别。页面在生成依据、实验标题和范围中标识无反馈对照；导出的报告保留反馈模式、输入 schema 和输入哈希。

## 预登记与封存

正式运行前保存基线哈希、代码协议哈希、任务包、模型 ID、运行顺序、预算、选择规则和停止规则。两组均完成有效验证后，各自选择已接受候选；拒绝则保留冻结初始版本。非法候选或执行异常不等同于完整质量判定，研究停止并保留证据，不自动替换为另一次成功实验。

封存报告比较冻结初始版本与最终选择。最终选择可以与初始版本相同，也可以是多代后代，但模型和 Harness 必须一致。如果两组最终选择同一版本，仅执行一份封存报告并明确共用；不把相同版本包装成两个不同改进版本。相同版本两列来自独立重复执行，结果标记 `same_version`，分数波动不解释为进化收益。

调用脚本（会产生真实模型费用）需要运行中的本地服务和已登记版本：

```sh
uv run --frozen --extra harbor python tests/manual_feedback_study.py \
  --plan docs/studies/2026-11-10-feedback-01-plan.json \
  --output .evoarena/studies/feedback-01
```

仓库里的计划固定了维护者本次实验的版本 ID；其他用户需创建自己的基线并重新登记计划，不能直接冒用这些版本。脚本使用固定幂等键，重启客户端会等待原实验，不重新生成候选；服务端中断仍遵循显式恢复协议。历史失败尝试与当前完整研究分别记录，不能只汇报最好的候选。

验证和封存都只有有限场景及两次重复，供应商未声明 seed 支持；单个候选对照只能描述这次实验，不能证明普遍有效或统计显著。
