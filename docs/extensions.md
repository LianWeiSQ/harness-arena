# 扩展 Evo 的三个入口

当前扩展方式是修改仓库并运行验证，还没有动态插件市场、任意脚本上传或外部 Worker 注册接口。每次扩展都应创建新的内容版本和实验，保留旧结果及其适用范围。

## 增加领域任务

先写清用户目标、公开工具契约、可观察状态和独立成功条件。开发、验证和封存应使用不同机制；只更换名称或金额不能证明跨机制泛化。

1. 在 `business.py` 增加场景和服务状态转换。服务在宿主机，Agent 只能调用公开动作。
2. 在 `taskpacks.py` 增加公开提示和分组，在 `fixtures/harness/business.cjs` 提供工具入口；检查帮助等读取操作不写业务状态。
3. 在 `verify-business.cjs` 独立检查最终状态、动作约束和签名。关键违规应可识别，不能用 Agent 回答代替验收。
4. 校准参考解、空操作、错误解，以及篡改签名、跨 Trial 账本和缺失结果；不能只验证正确解通过。
5. 把新增执行源码加入 `taskpacks.SOURCES`，确认 TaskPack 指纹改变。新实验使用新包，不覆盖历史。

开发反馈可进入优化器，验证和封存细节不进入本次候选生成。仓库公开，因此这里保证平台数据流隔离，不是对有权读取源码的人保密。封存结果用于最终报告，看过后继续调参必须披露这一事实。

## 增加 Harness 或注入面

入口是 `harbor_agents.py` 的 Harbor `BaseInstalledAgent` adapter 和 `harness.py` 的运行器映射。

| 必须声明或实现 | 核对内容 |
| --- | --- |
| `versions.CAPABILITIES` | 固定运行器版本、支持的注入面和不支持项 |
| 任务 Dockerfile | 锁定安装版本；运行时不自动发现个人配置 |
| adapter `install/run` | 使用本场中继，不向容器传供应商密钥 |
| `load_version` | 只读资产、CLI 版本、文件哈希和宿主加载收据 |
| `InputEvidence` | 真实请求中的策略/Skill；区分注册与正文读取 |
| 执行结束 | 异常时也写冻结标记；业务入口关闭后才能验收 |
| 用量和结果 | 经统一网关和独立验收收集，未知用量不记零 |

先用两个内容不同的版本做加载检查，再做业务配对。不能把任意文本前缀称为原生 Skill 支持，也不能把切换模型连接称为训练模型权重。

## 更换候选生成算法

`ImprovementExperiment.optimizer_factory` 目前生成 `BudgetedOptimizer`。替换算法仍须保留这些边界：

- 诊断只读取开发证据，引用对应真实 Trial/事件；验证和封存不进入生成输入。
- 只改变授权的一个现有文件，固定执行模型、Harness 和其他文件；更大范围须新增协议。
- 调用经过 `ExperimentBudget.claim/settle`，包括修正和生成；原始响应保存后再解析，恢复时复用。
- 生成器不能更新推荐。`evaluation.py` 检查覆盖和回归，`improvement.finalize` 再校验 epoch、版本和修订号并事务提交。
- 证明算法贡献需要同候选数、同评测预算的无开发反馈对照，报告失败尝试和总成本。

当前单候选流程不等同于种群搜索或 GEPA。记忆、检索、路由、工作流和协作需要新的资产定义、注入证明和指标，路线见 [总体规划](evo-platform-plan.md)。

## 提交前验证

运行锁定环境中的单元与契约测试、`calibrate-business` 和相关真实加载/配对实验；运行器更新还需从新目录安装。公开证据采用字段白名单导出，不提交本地配置、原始响应和 `.evoarena/`。

HTTP 接口定位为本地单用户。多租户或分布式 Worker 需要重新设计认证、隔离、领取租约和预算一致性，目录锁与 epoch 不能代替多机协议。
