# M1 版本加载实验

2026-11-10 完成第一组人工父子版本的真实加载实验。此阶段验证不可变资产能进入真实 Harness，并分别记录文件加载、模型输入和业务验收。没有自动候选生成，也没有晋升决定。结构化证据见 [m1-verification.json](m1-verification.json)。

## 如何使用

沿用 README 中的本地启动命令，访问 `/evo` 或根路径。模型连接仍在 `/settings` 配置。

1. 创建基线，选择模型与 Harness，填写可选执行策略和 Skill。
2. 从基线创建候选。模型与运行器锁定继承，修改策略或 Skill；空变更会被拒绝。
3. 展开“运行前检查所选版本的改动”，检查 diff。保存版本不会调用模型。
4. 点击“验证两个版本”，在两个独立环境里顺序运行订单回执任务。每次执行最多 12 次模型请求，累计 180,000 token 后停止下一请求，执行时限 240 秒。
5. 查看双方的加载核对、业务验收、Skill 正文进入上下文的记录、具体 diff 与工具轨迹。

当前是单任务加载检查，不产生质量提升或泛化结论，不切换推荐版本。服务重启保留已完成记录；运行中断只标记 interrupted，自动继续和取消将在 M4 实现。旧对比 `/harness`、旧进化记录 `/fixops` 保留。

候选把笼统的“读取错误，再决定下一步”改为“写入超时视为结果未知，先核对业务状态，再决定重试”，并增加最终状态核对。它由人工在页面中创建，不能描述成模型已自动进化。

这次记录还暴露了旧任务工具的局限：`arena-order submit --help` 没有被作为帮助请求处理，而是触发了真实的模拟订单提交。双方都发出了这种命令，同时存在并行查询。宿主轨迹先记录查询结果 0，再记录订单提交；不能把模型自述的“异步落库”当作已经证明的服务机制。基线随后再次提交，候选串行复查后停止提交。

因此本记录证明资产已生效、行为差异可追查，不能证明 Skill 在一般场景下稳定提升。M2 会修正工具参数与帮助语义，用显式、可重复的故障注入构建新任务包，保留这份旧结果与任务指纹。

另对 DSH `0.1.2-rc.1` 的任务指令前缀进行了真实单次执行验证：策略出现在模型输入，版本文件哈希一致，业务验收 2/2，5 次请求、48,135 token，23.93 秒，原有 ATIF 轨迹仍可生成。DSH 原生 Skill 能力继续显示为未验证，不作为支持能力开放。

## 核心实现与边界

- `versions.py` 注册只包含允许字段的版本，固化模型身份、运行器版本、策略和 Skill 文件。密钥不进入 manifest。候选不允许静默改变模型与运行器。
- SQLite 为 `evo_version` 增加不可变约束。实验意图和请求幂等记录同事务保存，重复请求不会新增付费任务。
- `HarborTrial` 为旧对战和新实验共用单次执行路径，版本目录通过只读挂载传入容器。
- adapter 在启动 Harness 前检查实际运行器版本与容器内文件哈希；模型网关独立观察真正发往 Provider 的策略、Skill 目录和正文，不把文件存在等同于模型已读取。
- Skill 目录注册与 Skill 正文读取分别显示；两者都不证明模型一定遵循流程。业务通过与否由独立验证器判定。
- 当前仍依赖相邻 Harbor 工作区中的 DSH adapter；独立分发与安装属于 M6。自动生成、重复配对评测和恢复未在 M1 中宣称完成。
