# 模型终止状态与用量

2026-11-10 的 `feedback-01` 研究在 6 次开发、2 次有效验证后停止。第 9 个 Trial 的业务账本已经满足验收，但最后一次模型回复异常且用量未知，因此该 Trial 无效，不能晋升候选。对照与封存尚未启动；完整记录见 [研究结果](studies/2026-11-10-feedback-01-result.json)。

旧记录只保留“模型响应异常或用量未报告”，没有供应商响应体或终止事件摘要。不能事后确定是流截断、非法 JSON、缺少用量还是解析问题，也不能把已经通过的业务账本改成完整 Trial。

排查时发现网关原先只读取 `response.completed`。Responses 同时存在 `response.failed` 与 `response.incomplete` 终止事件，二者的响应对象也需要独立核对用量；失败状态不代表零费用。[官方事件定义](https://developers.openai.com/api/reference/resources/responses/streaming-events)

修正后的行为：

- 按 SSE 事件帧读取多行 data，支持 CRLF 与注释；`[DONE]` 本身不作为完成证明。
- 要求一个状态一致的终止事件；缺失、冲突、无效格式分别记录。
- 先结算已报告的有效用量，再判定终止状态。已知费用的失败/未完成回复仍停止当前 Trial，不误计为未知用量。
- 未取得有效用量仍记为 unknown。超时、连接失败、HTTP 错误分别分类；不自动重新派发失败调用。
- 结算记录保存白名单摘要：响应字节数、SHA-256、格式、事件数、终止状态、用量是否已知和错误类别。导出再次过滤，不保存供应商错误正文、响应内容、URL 或密钥。

这项修正改善解析、记账与排障，尚不能证明它解决了旧实验中的具体异常。旧实验保持不可续跑的证据不足状态；如重新开展研究，必须登记新计划并保留所有旧结果。

本地协议回归覆盖多行 SSE、未完成/失败的已知用量、缺失/冲突/畸形终止事件、缺失用量、超时、读取中断、拒绝重派发及报告脱敏。真实接口预检安排最多 4 次小请求、8,000 Token 阈值；实际完成 SSE/JSON 各 1 次，共 2 次请求、8,806 已知 Token、0 未知，下一次请求被预算阻止。阈值是调用前检查，最后一次返回可跨越阈值；未将被阻止的请求计为已发出。预检不替代真实 Harness 的完整协议。

## 第二次传输中断与读取方式修正

`feedback-02` 在 22/24 次有效验证后停止：228 次调用、1,538,016 已知 Token、1 次未知；失败调用持续约 195.88 秒，分类为 `transport_error`。现有记录不能区分具体的底层异常类型。对照和封存未启动，29 组资源全部清理。见 [完整停止报告](studies/2026-11-10-feedback-02-result.json)。

原网关会缓冲整个 HTTP 响应直到连接结束，即使 SSE 已经给出终止事件，也可能继续等待 EOF。现在按事件逐步读取，收到终止事件后立即停止读取并核对状态与用量。有限本地服务器测试发送完整响应后故意保持连接，验证网关无需等连接关闭。此测试证明读取缺陷已修正，不证明它就是上面那次中断的根因。

传输中断时保留已收到的部分字节用于解析，摘要增加标准异常类型、读取结束方式和耗时；不公开响应正文。部分响应若有可核对的用量则照实结算，但读取异常仍使 Trial 无效，不重放请求。SSE 在读取间检查截止时间，底层仍有 socket 空闲超时；这不是对正在阻塞读取的硬实时取消保证。完整终止事件之后的连接关闭不再是模型完成的必要条件。

## 修正后的有限真实检查

代码 `a9feef4` 的 [检查收据](transport-compatibility-verification.json) 记录了两种请求和一次真实 Pi 加载检查：

- SSE、JSON 各发一次随机文本回显请求，均正确返回，共 8,836 已知 Token、0 未知用量。SSE 的读取结束方式为 `terminal`，JSON 为 `eof`。
- Pi 实验 `ex-ab2f5383f6e6` 预设最多 24 次调用、240,000 Token、1,200 秒。前三次 SSE 已成功返回终止事件，Pi 随后继续执行和请求；因此实际运行器能消费这种返回方式。
- 第四次请求在北京时间 19:43:38–19:43:39 收到上游 HTTP 502，调用时长约 1.03 秒。实验停在基线 Trial，候选未运行，共 4 次调用、17,820 已知 Token、1 次未知；唯一 Trial 资源已清理。

小请求检查与 Pi 检查合计 6 次调用、26,656 已知 Token、1 次未知。502 未被自动重派发，也未当作零费用或策略退化。完整兼容检查仍未通过，未启动下一轮完整研究。

这次可以明确定位为上游 HTTP 错误；不能据此把 `feedback-01/02` 的旧异常改写成同一根因。下一步需要网关请求日志或可验证的稳定连接，再登记新的研究计划；终态失败研究保留原结果。
