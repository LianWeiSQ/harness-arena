# Harness 自改进平台总体规划

更新日期：2026-11-10。工作名 Evo，代码包与仓库暂沿用 EvoArena / harness-arena。状态：规划已形成，v0.2 实现尚未完成。执行清单见 [TASKS.md](../TASKS.md)，技术边界见 [架构方案](evo-architecture.md)。

## 产品目标

帮助 Agent 开发者从真实执行记录中发现问题，生成可检查的修改，在相同条件下验证效果，并保留可复用、可回滚的版本。主操作是“改进这个 Agent”，核心交付是版本包和验证证据。

平台优化的是一个 Agent 系统：运行器、指令、Skill、工具、上下文规则和模型配置共同决定它的行为。优化哪一部分，由实验声明和运行器的能力决定。模型选型与路由属于配置优化；训练模型权重属于后续独立训练流程。

首要用户是有可运行 Agent、实际失败案例和验收标准的开发者。开源用户需要接入自己的运行器和任务，面试演示需要讲清楚一次改动的来源、执行过程、判定和恢复边界。

| --- | --- | --- | --- |

| 执行策略 | 规划、重试、进展检查、验证时机、停止条件 | 更可靠的任务完成方式 | v0.2 先做可配置策略，运行器内部控制流后续扩展 |

| 经验与记忆 | 从失败提炼规则、经验适用条件、冲突处理、失效与遗忘 | 可审计、可删除、可做消融的经验库 | v0.3 |
| 模型与路由 | 模型选择、不同步骤路由、推理预算、失败回退 | 质量与成本之间的可验证取舍 | v0.3；v0.2 保留模型设置与快照 |

| 知识与检索 | 查询改写、分块、召回、重排、引用和知识时效 | 在领域任务上的检索质量提升 | v0.4 领域扩展 |
| 多 Agent 协作 | 分工、委派、审查、交接信息、重复劳动控制 | 可测量的协作收益 | v0.4，先有单 Agent 基线 |
| 人机协作 | 何时澄清、何时请求确认、如何减少无效打断 | 自动完成率与人工介入成本报告 | v0.4，权限边界由用户配置 |
| 训练数据 | 高质量轨迹筛选、失败标注、偏好对、数据来源记录 | 可交给外部训练系统的数据集 | 后续插件；权重训练不属于 v0.2 |

这些方向共用版本、实验、运行、轨迹和判定体系。某个适配器不能控制的维度必须显示为不支持，不能保存了配置就宣称它已生效。v0.2 不宣称上述能力全部已实现。

## 平台需要提供的六项能力

1. **接入与版本管理。** 注册运行器、模型连接和 Skill 文件，记录实际加载的文件、内容哈希、运行器版本和环境。输入既支持人工提交候选，也支持后续优化器生成候选。
2. **诊断。** 汇总失败类型和无效步骤，引用具体运行与事件，给出“观察、假设、拟修改对象、验证方法”。证据不足时保留未知，模型给出的原因先作为假设。
3. **候选生成。** 从允许修改的范围生成小幅变更，输出 diff、理由与预期影响。先单因素，再考虑组合优化。候选生成器是可替换接口。
4. **可信评测。** 配对运行、独立验收、数据分组、重复运行、回归检查、预算计量和基线对照。评测器不受被优化 Agent 修改。
5. **可靠实验执行。** 实验级预算、取消与恢复、幂等创建、持久检查点、资源清理，以及明确的失败分类。
6. **交付与复用。** 导出策略包、完整配置与脱敏报告，切换本地推荐版本并可回滚；后续通过 CLI/SDK 和 CI 接入已有项目。

Arena 保留为候选对比视图。谱系用于解释版本来源，曲线用于解释固定任务集上的变化；赛季、席位、积分不再组织新产品的主流程。

## 首个领域与后续领域

v0.2 默认选择“业务工具 Agent 的可靠执行”，用异常订单处理作为易理解的演示。Agent 实际调用隔离测试服务，订单与业务数据属于模拟环境；验收检查服务端最终状态和操作过程。

| 问题族 | 任务例子 | 可检验的能力 |
| --- | --- | --- |
| 操作成功但回执丢失 | 请求超时后确认订单是否创建，避免重复提交 | 查询后再决定重试、识别未知副作用 |
| 查询结果不完整或暂未更新 | 分页、延迟状态导致 Agent 误判不存在或已完成 | 完整查询、限次等待、证据核对 |
| 多步骤部分成功 | 订单修改与库存预留只完成了一部分 | 识别中间态、恢复或补偿、核对最终一致性 |

每个问题族要有正常解、典型错误解、稳定的故障注入和独立验证器。不同实例改变业务条件、响应结构、故障时序或所需操作；仅改名称、端口和 ID 不算不同机制。

后续任务包依次考虑企业知识问答、客服与售后流程、代码维护。它们分别推动检索与记忆、人机协作与工作流、工具与上下文管理。既有进程清理任务保留为兼容性案例，不作为新产品首页的解释主线。

## 一次实验的完整路径

用户选择基线版本、任务包、允许改动的维度、优化目标和预算。平台在执行前固化实验清单，然后运行基线、归纳证据、提出假设、生成候选、验证候选，最后记录接受、拒绝或证据不足。接受只更新本地项目推荐版本，不自动部署到外部生产系统。

一次候选详情必须回答：为什么改、改了什么、运行器是否真的加载了改动、在哪些任务上有效、出现哪些回归、花了多少预算、为什么做出最终决定。连续循环只能在预算、候选数和停止条件内运行。

默认一次只演化一个运行器版本，其他维度冻结。跨 Harness、跨模型迁移是单独实验；不能把更换模型后的收益全部归因于 Skill 改进。

## 评测与优化协议

- **任务分组。** 最低配置为 3 个问题族、18 个实例，开发/验证/封存各 6 个；按业务模板和故障机制分组，避免近重复样本跨组。属于小样本机制验证，不用于宣称行业领先或统计显著。
- **信息隔离。** 优化器只读取开发集的任务与轨迹。验证集可以参与版本选择，但其详细任务、答案和轨迹不回流候选生成。封存集只用于最终报告，不参与本次选择；开始后更改分组必须新建实验。
- **重复与配对。** 验证和最终报告至少 2 次重复，按任务、重复编号、环境和预算配对，记录顺序与随机性设置。不支持 seed 的模型明确记录，不能承诺逐 token 复现。
- **首个晋升规则。** 质量优先：有效覆盖完整，各任务重复后的成功数不低于父本，总成功数严格增加，关键业务约束零违例。规则在实验前冻结。该规则是保守操作门槛，不等于统计显著性检验。
- **效率目标。** 之后允许预先声明质量不退化约束下的 token 或耗时优化。报告成功任务的条件效率与全体任务的总成本，避免只保留成功样本造成偏差。未配置价格时只报告 token，不编造货币成本。
- **基线。** 始终保留不进化的初始版本。除逐代父子对比，还比较最终选中版本和初始基线。对“反馈驱动优化有贡献”的结论，需要增加同候选数、同评测预算、移除失败反馈的候选生成对照。
- **失败分类。** 任务失败、预算耗尽、供应商故障、环境错误、非法候选、回归、无收益、证据不足分别记录。缺失样本不直接当作失败或零成本，也不能删除后继续宣称完整覆盖。
- **停止条件。** 候选数上限、实验调用/token/时长预算、连续无收益、用户取消。模型响应的 token 可能跨越阈值，派发前预检与派发后记账都保留。
- **评测体系版本。** 任务、验证器、指标与阈值可单独迭代，但每次变更建立新版本。生成候选的 Agent 无权修改本次评分器、任务答案和晋升规则。

开发集反馈参与生成，验证集参与选择，因此验证分数有选择偏差。封存结果和控制实验用来暴露这个差距。拒绝了所有候选仍然可以完成一次有效实验。

## 产品与交互

新导航采用“总览 / 实验 / 版本 / 任务集 / 设置”。第一次打开没有数据时展示接入步骤与已标注的真实回放入口。

| 页面 | 主要内容 | 主要操作 |
| --- | --- | --- |
| 总览 | 当前基线、正在改进的问题、最近判定、剩余预算 | 发起改进实验 |
| 实验 | 配置、阶段进度、诊断证据、候选变更、逐题结果 | 取消、从可确认的边界继续、导出 |
| 版本 | 实际组成、父子关系、diff、适用任务、已知退化 | 选为基线、查看证据、切换推荐版本 |
| 任务集 | 业务目标、问题族、分组、验收规则与数据版本 | 校准、选择任务包 |
| 设置 | 模型连接、运行器能力、默认预算、数据目录 | 保存、检查依赖 |

视觉延续已采用的米白、黑色细线、蓝色与橙色，图表紧凑。蓝色表示基线，橙色表示候选；接受/拒绝同时显示文字和符号。首页突出“本次改了什么、验证结论是什么”，原始日志放到证据详情。成长曲线必须锁定任务集和评测协议，跨协议用分段展示。

## 模块与复用

| 模块 | 现有基础 | 新增或调整 |
| --- | --- | --- |
| 运行器适配 | DSH/Pi Harbor adapter | 能力声明、版本包加载、加载收据、独立安装 |
| 模型配置 | 本地设置、密钥隔离 | 模型身份快照、生成模型/执行模型分开计量 |
| 版本库 | FixOps 不可变策略与父子关系 | 可组合 AgentVersion、内容哈希、导入导出 |
| 实验控制 | 单机顺序运行、请求去重 | Experiment/Trial、实验级预算、检查点与继续 |
| 诊断与优化 | FixOps mutation 原型 | 标准化证据、假设、受限 patch、优化器插件 |
| 评测与判定 | Harbor、独立验收、同题比较 | TaskPack 分组、多次配对、判定协议、封存报告 |
| 前端 | 设置页、比较表、轨迹与补丁 | 围绕改进实验重新组织信息 |
| 开源交付 | README、测试、GitHub 仓库 | 消除本机相邻仓库依赖、脱敏回放、扩展指南与 CI |

M1 已将 Pi 的显式 Skill 路径与系统策略追加接入不可变版本，保留自动发现关闭以隔离本机配置；DSH 的任务指令前缀也已实测。旧版自动策略进化仍只影响 FixOps，新工作台当前运行人工候选。加载证据见 [M1 实验](version-loading-check.md)。DSH 与 Pi 不支持相同内部机制时保留各自能力边界，不用统一字段制造兼容假象。

| 阶段 | 产物 | 验收门 | 依赖 |
| --- | --- | --- | --- |

| M1 版本与接入 | AgentVersion、适配能力、人工候选、最小实验页面 | 两个不同版本实际加载不同内容并留下哈希；旧历史可访问 | M0 |
| M2 任务与评测 | 自包含业务任务包、配对协议、预算与校准 | 3 类问题/18 实例；正常与错误解可被验收器区分；分组冻结 | M1 |
| M3 自动改进 | 诊断、候选生成、配对验证、事务判定 | 至少一种真实 Harness 跑通模型生成候选到接受或拒绝全链路 | M2 |
| M4 可靠运行 | 持久计划、取消、检查点继续、资源对账 | 重启不丢已完成记录，不重复不确定副作用，陈旧晋升被拒绝 | M3 |

每阶段以可检查产物完成，不用“界面已改名”代替闭环完成。实现发现能力不支持时，先更新能力矩阵和方案，再选择受支持的变更面。

## 长期 Goal 与完成条件

**主 Goal：在现有仓库交付可本地复现、具有真实候选生成与证据化判定的 Harness 自改进平台 Evo v0.2。**

1. DSH/Pi 基线执行与模型设置继续可用，至少一种运行器真实加载并演化 Skill 或策略配置；支持与不支持的维度清晰可见。
2. 版本、实验、运行、诊断、候选、评测、判定与产物相互关联；所有晋升有可检查的具体改动和有效验证结果。
3. 3 类问题、至少 18 个实例、三类数据分组和至少 2 次配对重复形成可重放的实验协议。
4. 至少一次真实模型生成候选并完成接受/拒绝；展示真实失败或无收益结果，自动化测试另覆盖晋升成功和回归拒绝。
5. 冻结初始基线、封存报告、同搜索预算的反馈消融对照，以及全实验成本报告可导出；不保证实验有正收益。
6. 预算、取消、重复请求、崩溃后继续与回滚有测试证据；未知副作用不盲目重放。
7. 完成围绕改进的 UI、本地启动、脱敏回放、扩展文档和面试演示；全新目录运行不依赖开发者的相邻私有仓库。
8. 本阶段必要验证完成，任务范围内的改动提交并推送 `LianWeiSQ/harness-arena`。

v0.3/v0.4 能力地图不计入本 Goal 的完成条件。近期不建设多租户托管、分布式集群或 GPU 训练平台；出现并发、部署或训练需求时再启动独立阶段。

## 外部方法与工程边界

Harbor 官方定位包含沙盒任务的评测和优化，现有项目继续使用其执行与验证能力。[Harbor 文档](https://docs.harborframework.com/)

候选生成接口可借鉴从执行轨迹中反思并生成文本变更的方法；GEPA 的论文给出了这类方法，但其论文结果不代表本项目已经获得收益。先用可解释的单候选闭环建立基线，再评估是否接入完整搜索算法。[GEPA 论文](https://arxiv.org/abs/2507.19457)

项目的交付重点是把真实运行器、可改进资产、独立验收、可靠执行和可导出的证据连起来。优化器算法可以替换，任务与版本契约保持稳定。
